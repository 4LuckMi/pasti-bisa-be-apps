Ringkasan sistem

Backend berbentuk modular monolith Spring Boot 4.1.2 / Java 25. Satu image menjalankan proses API dan proses worker terpisah. PostgreSQL 17 menyimpan akun, konten terversi, sesi, jawaban, hasil, metadata file dan job persisten. PDF berada di storage disk privat yang dibagi API/worker. Login menggunakan session cookie, baik melalui password maupun Google OAuth2/OIDC; mutasi memakai CSRF.

Flow yang tersedia: register/login → pilih katalog/topik → start/resume → simpan jawaban → finalize → worker scoring → hasil/review. Petugas mempunyai flow PDF → kandidat → koreksi → draft → publish → versi baru/arsip.

Arsitektur dan alur backend

Indeks dokumentasi · Model data · API

Runtime

Compose mempunyai tiga service: postgres, api, worker. API dan worker memakai image yang sama, namun worker memakai profil worker, mengaktifkan scheduler dan tidak membuka HTTP listener publik. API menjalankan HTTP di port container 8080. Flyway berjalan saat startup; PostgreSQL mengunci proses migrasi agar dua proses tidak menerapkan versi yang sama bersamaan.

Antrean memakai tabel job, bukan broker terpisah. Redis, S3/object storage, message broker, gateway payment, SMTP dan reverse proxy produksi belum terintegrasi. Session masih berada di memori proses API.

Pola ini memisahkan tanggung jawab, tetapi belum merupakan isolasi modul yang sepenuhnya dipaksakan oleh build. SQL berada pada adapter persistence dan memakai named parameter, bukan string gabungan dari input pengguna.

Identitas, tipe pengguna dan hak akses

user_type adalah klasifikasi produk, saat ini default SISWA. user_role adalah izin; satu akun bisa mempunyai beberapa role. Pendaftaran publik tidak menyediakan pilihan role dan selalu memberi CUSTOMER. Kode role yang disiapkan: CUSTOMER, QUESTION_STAFF, PLATFORM_ADMIN.

PLATFORM_ADMIN bukan superuser otomatis. Agar akun admin membuka konten, akun tersebut harus diberi QUESTION_STAFF secara eksplisit. Sejumlah read API lama hanya mengecek authenticated, belum role CUSTOMER; penyamaan policy read API dicatat sebagai pekerjaan penguatan akses.

Login/register password

Register mendapat 201, login 200. Tidak ada access/refresh JWT pada response aplikasi. Cookie server adalah identitas session. Default idle timeout 30 menit, dapat diubah melalui SESSION_TIMEOUT. Restart/recreate API menghapus session. Logout menghapusnya segera.

Google OAuth2/OIDC

Profil oauth menambahkan provider Google dengan scope openid,profile,email. Service menolak email tidak verified dan akun lokal tidak aktif. Akun baru SSO boleh memiliki password_hash=NULL; akun tersebut tidak otomatis dapat login password. Saat subject belum terhubung, service saat ini dapat menautkan akun berdasarkan email Google yang verified. Penguatan/persetujuan kebijakan linking dicatat sebelum peluncuran produksi. Client Secret hanya berada di konfigurasi server; jangan dimasukkan ke frontend, Postman atau dokumentasi. OAuth state/nonce menjaga proses login/callback. CSRF token menjaga mutasi aplikasi yang memakai cookie session; mengaktifkan Google SSO tidak menghapus kebutuhan CSRF untuk profil, jawaban, upload atau logout.

Start tryout/practice

Lock akun dan unique index sesi aktif mencegah dua start paralel. Key berlaku per user; body hash mencakup mode, target dan jumlah soal. Replay bukan membuat sesi baru, walaupun sesi lama sudah selesai. Bila key baru dikirim sementara sesi aktif/finalizing masih ada, response tetap sesi itu dan key baru belum dipakai untuk attempt baru. Client harus membaca mode, tryoutId dan status response.

Tryout: paling banyak dua start baru per hari WIB. Practice: 1–50 soal, durasi teknis dua menit per soal, blueprint internal per kombinasi topik/jumlah, tanpa pemotongan kuota tryout. Durasi ini belum konfigurasi produk terpisah. Keduanya berbagi satu sesi IN_PROGRESS/FINALIZING.

Pool memakai versi PUBLISHED terbaru per soal, tidak diarsipkan, cocok subtes/topik/tahun. Pemilihan mengutamakan belum dilihat lalu paparan tertua. Pada tryout baru, soal yang dilihat pada hari WIB yang sama dikeluarkan; query exposure saat ini juga mencakup practice. Soal diacak setelah pool dipilih. Opsi diacak hanya jika shuffle_allowed=true. Section yang bertumpang tindih sehingga memilih soal sama ditolak, bukan dicari ulang.

ready pada detail katalog menggambarkan stok global, belum stok personal sesudah filter paparan harian. Karena itu ready=true belum menjamin start pengguna tertentu berhasil.

Autosave, deadline dan penilaian

Revision awal belum ada jawaban adalah 0; penyimpanan pertama menjadi 1. Update berikutnya wajib membawa revision terakhir. selectedOptionId=null mengosongkan pilihan; jawaban bisa tetap ditandai flagged. Server memvalidasi opsi milik versi soal tersebut. Waktu client tidak menentukan apakah jawaban diterima.

Finalize biasa, abandon dan deadline sama-sama menuju FINALIZING, dengan terminal reason SUBMITTED, ABANDONED atau TIMED_OUT. Worker mencari maksimal 100 sesi kedaluwarsa per tick; GET sesi/hasil tertentu juga dapat memfinalisasi sesi yang sudah kedaluwarsa. Request answer terlambat ditolak, lalu worker/read sesi menutup statusnya.

Hasil yang belum ada: totalScore=null, sections=[]; UI menampilkan menunggu pemrosesan. Review hanya setelah COMPLETED. Baca satu soal juga membuang kunci/pembahasan sampai ada score_run. Sesi abandon tetap menghabiskan kuota dan boleh memiliki hasil pribadi.

Rumus penilaian yang tersedia

  • BINARY: poin benar/salah/kosong dari policy; default 1/0/0. Maksimum per soal adalah correctPoints.
  • OPTION_WEIGHT: poin opsi terpilih; maksimum per soal adalah bobot opsi tertinggi. Opsi kosong memakai emptyPoints default 0.
  • totalScore = jumlahPoin × scale / jumlahMaksimum, dibulatkan 4 desimal HALF_UP.
  • Akurasi section = benar/jumlah soal × 100, terpisah dari nilai berbobot.
  • Policy awal hanya mendukung agregasi SUM, rounding HALF_UP dan rule yang dikenali; selain itu start ditolak.

Ini indeks latihan PastiSiap, bukan nilai resmi UTBK/IRT atau keputusan kelulusan. Sesi acak tidak otomatis menjadi leaderboard kompetisi karena belum memakai form/cohort sebanding.

PDF menjadi bank soal

Input parser: nomor soal, opsi A–E, Kunci: B, Pembahasan: .... Missing/ambiguity tidak ditebak. Draft koreksi disimpan terpisah dari hasil ekstraksi agar provenance tetap terlihat. Simpan kandidat idempoten; setelah tersimpan, perubahan dilakukan sebagai versi master baru. Publish tidak otomatis dilakukan worker. Versi DRAFT terbaru tidak menghilangkan versi PUBLISHED lama dari pool sampai versi baru diterbitkan.

PDF sumber bisa mengandung kunci, sehingga role siswa tidak mendapat akses sumber. Asset siswa menggunakan purpose QUESTION_ASSET; sumber menggunakan IMPORT_SOURCE dan diblokir menjadi asset siswa. API upload asset gambar/biner terpisah belum tersedia. File yang sudah terdaftar dapat dibaca melalui endpoint asset.

Worker dan batas transaksi

Polling default tiap dua detik; satu job dikerjakan per tick. Retry menunggu 10 detik, maksimum default lima percobaan menurut kolom job, lease 15 menit. Worker tidak memiliki API retry manual. Job gagal permanen membutuhkan investigasi operator; attempt dapat tetap FINALIZING tanpa menampilkan skor nol.

Token lease mencegah worker lama menandai sukses/gagal atas job yang sudah dimiliki worker baru. Commit hasil impor juga memverifikasi lease. Scoring sendiri mengunci attempt dan berhenti jika sudah COMPLETED; commit score aman diproses ulang setelah worker crash sebelum status job berhasil ditulis.

Use case Batas transaksi

Start Lock akun, replay/active check, pool, attempt/items dan kuota berada pada satu transaksi
Answer Lock attempt dan update bersyarat revision
Finalize Perubahan status + enqueue scoring atomik

Upload Tulis file dahulu; transaksi metadata + batch + job; cleanup file bila gagal/duplikat

Filesystem dan PostgreSQL tidak membentuk transaksi terdistribusi. Crash di sela upload dapat meninggalkan file orphan; rekonsiliasi/retensi storage dan backup terkoordinasi masih pekerjaan operasional berikutnya. Audit konten sudah ada, tetapi koreksi kandidat dan semua tindakan auth belum menjadi audit lengkap.

Logging dan penanganan error

Request mendapat X-Request-ID; error body memakai requestId sama. Log mencatat method, path tanpa query, status, durasi, kode error; 4xx WARN, 5xx ERROR beserta stack trace. Body, cookie, password dan token tidak dicatat. Worker memakai korelasi job:<uuid>. Client tidak menerima stack trace/SQL.

Respons error standar dijelaskan pada referensi API. Kasus binary asset tidak ditemukan secara eksplisit mengembalikan 404 dengan body kosong, sehingga client tidak boleh selalu mengasumsikan body error JSON.

Model data, struktur JSON dan ERD

Indeks dokumentasi · Kamus kolom lengkap

Skema aplikasi terdiri dari 40 tabel pada migrasi V1–V6, di luar flyway_schema_history. ERD di bawah memakai nama camelCase untuk keterbacaan; nama tabel SQL padanannya adalah snake_case. Diagram menunjukkan relasi utama, sedangkan seluruh foreign key/composite constraint ada pada kamus tabel.

Identity dan profil

  • email_canonical menyimpan email untuk lookup unik; service menormalisasi lowercase/trim.
  • password_hash berupa BCrypt, dapat NULL pada akun SSO; tidak pernah menjadi field response.
  • user_type default SISWA adalah tipe produk, sementara role berasal dari relasi user_role.
  • oauth_account mengenali identitas eksternal dengan pasangan provider+subject, bukan email saja. Unique user+provider membatasi satu identitas provider yang sama per akun.
  • Trigger pembuatan akun menambahkan user_profile. Update profil menyinkronkan display name akun/profil.
  • TargetKind tersimpan sebagai CAMPUS/CIVIL_SERVICE/ACADEMY/SCHOOL, hasil mapping dari kategori form siswa.
  • Token reset/verifikasi mempunyai hash dan expiry, tetapi flow endpoint/mail belum tersedia.

Konten, asal file dan versi

question adalah identitas keluarga soal: subtes, topik, kode, asal kandidat dan archive timestamp. Konten ada pada question_version; opsi juga terikat pada versi. Edit terbit membuat versi baru, bukan mengubah versi lama. Pool memilih versi PUBLISHED terbaru; versi DRAFT yang lebih baru tidak ikut pool. Soal diarsipkan pada keluarga question, sehingga sesi baru tidak memilihnya, sementara sesi lama tetap dapat dibaca.

Sumber PDF disimpan satu kali per upload yang diterima, bukan disalin per pengguna/attempt. stored_file memuat path relatif, checksum, ukuran, MIME, pengunggah, original name dan purpose. import_batch memuat scope dan hitungan kandidat; import_candidate menyimpan asal halaman/item, ekstraksi asli dan draft koreksi terpisah. Unique batch+page+item membuat commit ekstraksi ulang idempoten. Unique question.candidate_id menjaga satu keluarga soal per kandidat yang disimpan. Tidak ada penggabungan otomatis terhadap soal berteks mirip dari file berbeda.

Tiga bentuk data soal yang berbeda

Database question_version.stem dan question_option.content:

{"text":"Berapa hasil 2 + 3?"}

Request authoring/kandidat berupa konten terstruktur dengan opsi dan kunci:

{
  "stemText": "Berapa hasil 2 + 3?",
  "options": [
    {"code":"A","text":"4","correct":false,"weight":0},
    {"code":"B","text":"5","correct":true,"weight":1}
  ],
  "explanation": "Dua ditambah tiga sama dengan lima.",
  "shuffleAllowed": false
}

Response soal siswa saat aktif mempunyai key berbeda dan tidak membuka kunci:

{
  "position": 1,
  "stem": {"text":"Berapa hasil 2 + 3?"},
  "options": [
    {"id":"00000000-0000-4000-8000-000000000011","code":"B","content":{"text":"5"},"correct":null},
    {"id":"00000000-0000-4000-8000-000000000012","code":"A","content":{"text":"4"},"correct":null}
  ],
  "selectedOptionId": null,
  "flagged": false,
  "revision": 0,
  "correct": null,
  "explanation": null
}

code adalah kode opsi master, id adalah identitas database opsi, dan posisi tampil berasal dari snapshot. Frontend mengirim selectedOptionId, bukan huruf berdasarkan urutan tampilan. correct=null bisa berarti hasil belum tersedia atau soal kosong; periksa status attempt dan selectedOptionId.

Blueprint, snapshot, jawaban dan hasil

blueprint adalah identitas paket yang ditampilkan katalog; active_version_id memilih konfigurasi aktif. blueprint_version mengikat durasi dan scoring policy; section mengikat subtes/jumlah/filter. Practice memakai mode PRACTICE pada blueprint internal yang tidak muncul di katalog TRYOUT.

Snapshot berupa referensi ke versi immutable, bukan salinan seluruh JSON soal pada setiap attempt. attempt_item membekukan question ID, version ID, section, nomor dan urutan kode opsi. Contoh option_order:

["B","A","D","C"]

answer menyimpan jawaban terakhir per item beserta revision, bukan event log seluruh perubahan jawaban. Belum ada tabel event untuk merekonstruksi semua autosave sebelumnya. Jam received_at berasal dari server/database. Revision 0 berarti belum ada record jawaban; insert pertama revision 1. Update stale ditolak.

Contoh filter section yang dipahami use case saat ini:

{"topicId":"00000000-0000-4000-8000-000000000021","sourceYear":2026}

Kedua field opsional. Filter lain ditolak saat start. Konfigurasi filter belum dibuat lewat API admin.

Contoh policy/rincian skor:

{"correctPoints":1,"wrongPoints":0,"emptyPoints":0}
{"label":"Indeks latihan PastiSiap; bukan skor resmi","correct":2,"wrong":0,"empty":1}

Policy adalah data terversi yang direferensikan blueprint dan hasil. Hasil menyimpan policyVersion, input hash, total dan rincian subtes. Unique hasil mendukung koreksi terversi di schema, tetapi API koreksi/regrade belum ada. Service normal menghasilkan satu score run dan mengembalikan hasil terbaru. correction_version default 1.

Lifecycle yang dipakai service

Terminal reason terpisah dari status. ABANDONED/TIMED_OUT saat ini adalah reason yang disimpan pada attempt, bukan status akhir yang harus ditunggu UI. Job gagal permanen tidak otomatis membuat status attempt FAILED. UI menunggu COMPLETED untuk review dan perlu menampilkan pemrosesan jika score masih null.

Commerce dan kompetisi yang masih sebagian

Diagram ini menunjukkan relasi schema, bukan flow pembayaran/kompetisi yang sudah aktif. Order menyimpan snapshot paket; satu order hanya boleh mempunyai satu entitlement grant. Event provider unik mendukung dedup webhook yang akan dibangun. Nilai uang memakai amount_minor BIGINT + currency; belum ada API untuk checkout atau konversi minor unit. Read subscription mengecek grant yang aktif, tidak cukup status langganan saja.

Kompetisi membutuhkan form tetap dan policy sebanding. Constraint leaderboard memeriksa kesesuaian form, score, pengguna dan opt-in. Sesi acak saat ini tidak memiliki form/cohort yang otomatis di-enroll.

Struktur job, audit dan file

Contoh payload job, tanpa password/token atau seluruh isi file:

{"attemptId":"00000000-0000-4000-8000-000000000031"}
{"batchId":"00000000-0000-4000-8000-000000000041"}

type menentukan dispatcher SCORE_ATTEMPT/IMPORT_PDF. dedup_key seperti score:<id> atau import:<id> unik. Kolom lease_owner, lease_until dan lease_token mengatur kepemilikan proses; retry_count bertambah saat claim. last_error menyimpan kelas exception yang aman, sedangkan detail penyebab ada di log.

Batch dan job mempunyai status berbeda: batch dapat QUEUED/READY/NEEDS_INPUT/FAILED; status pekerjaan dapat QUEUED/PROCESSING/RETRY_WAIT/SUCCEEDED/FAILED. Batch tidak harus mendapat nilai PROCESSING saat worker sedang berjalan. READY berarti kandidat lengkap menurut validator, bukan seluruh soal sudah dipublish.

audit_event dapat menampung aktor, aksi, entity, timestamp dan before/after tersensor. Implementasi konten saat ini hanya mengisi sebagian field/aksi; request_id dan before/after tidak otomatis terisi pada semua audit. Jangan menganggap audit_event sudah menjadi event sourcing seluruh sistem.

Layout file saat ini:

storage/
  imports/<uuid>.pdf           # sumber PDF privat, metadata di stored_file
  demo/sample-questions.pdf    # fixture dari profil demo, bukan asset siswa otomatis

relative_path direkonstruksi melalui adapter yang memeriksa normalisasi/realpath. Nama file pengguna tidak menentukan lokasi simpan. File asli tetap bisa berisi data sensitif/kunci dan hanya disediakan lewat handler petugas.

Konvensi tipe data dan evolusi

  • UUID dikirim sebagai string UUID pada JSON, diparameterkan sebagai UUID pada JDBC.
  • Timestamp memakai TIMESTAMPTZ/UTC, response ISO-8601; tanggal kuota eksplisit Asia/Jakarta.
  • Skor dan bobot NUMERIC/BigDecimal; jangan menghitung ulang score resmi di browser.
  • JSONB dipakai untuk konten fleksibel, filter, payload dan detail; identitas/relasi utama tetap kolom/FK.
  • Array list kosong sah. Nilai NULL punya makna berbeda dengan 0 atau string kosong.
  • Migrasi V1–V6 immutable. Tambahkan V7+ untuk perubahan schema berikutnya; jangan memakai ddl-auto=update.

Konvensi request dan response

  • Header Content-Type JSON untuk body JSON; upload memakai multipart dengan part metadata application/json.
  • GET tidak mempunyai body kecuali dinyatakan lain. Path ID memakai UUID; position nomor mulai 1.

  • Field camelCase/snake_case mengikuti DTO aktual. Semua key dijelaskan pada kamus DTO; tidak ada key password/token pada response user.

Java 25 ada pada container build/runtime. Laptop dengan Java 18 tetap dapat menjalankan stack melalui Docker. Jika menjalankan Maven langsung di laptop, gunakan JDK 25 dan PostgreSQL yang dapat diakses.

SERVER_PORT=8080

SPRING_PROFILES_ACTIVE=demo
COOKIE_SECURE=false

docker compose up --build -d
docker compose ps
docker compose logs -f api worker

API: http://localhost:8080/api/v1/health, Swagger: http://localhost:8080/swagger-ui.html, OpenAPI: http://localhost:8080/api-docs. Worker diperlukan untuk scoring, expiry dan impor, bukan hanya API.
